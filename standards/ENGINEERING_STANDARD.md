# 工程硬标准

本标准适用于生产源码、原生实现、框架桥接、配置插件、测试、构建脚本、发布产物和共享测试工程。“必须”和“禁止”均为强制要求。

## 一、插件优先

1. 插件是能力与代码所有权边界，也是唯一事实来源。
2. 平台原生实现、框架适配器、公共契约、测试和打包逻辑必须归属对应插件。
3. `plugin.yaml` 只声明已经实现、持续维护、可独立构建且可独立验证的交付目标。
4. 不支持的目标不枚举、不创建空目录、不编写占位接口或空实现。
5. 各平台实现可以不同，但公共字段必须同名同义；平台独有能力必须显式隔离。
6. 原生核心源码不能复制到多个适配器目录。单一产物有自包含要求时，由打包过程从规范模块组装。
7. Android、iOS、HarmonyOS、React Native、UniApp 和 Web 共享测试工程只验证公开接口，不拥有插件实现，不包含正式业务逻辑。
8. 共享测试工程必须消费最终交付形态，禁止通过源码工程依赖、工作区源码映射或复制实现来替代产物接入验证。
9. 真实业务项目只承担已发布版本的下游接入冒烟，不得成为插件源码的事实来源或发布前唯一验证环境。

## 二、上线质量

所有进入仓库的实现都必须满足上线质量：

- 公共行为明确、确定、可验证。
- 修改状态或资源前先完成边界校验。
- 错误结构稳定、可定位并如实传播，不能伪装成成功。
- 生命周期、取消、并发、线程或队列归属、资源释放必须明确。
- 不能提交密钥、签名材料、机器专属路径和无合法分发依据的依赖。
- 运行时代码不能包含占位实现、关闭的未完成功能、无说明的全量捕获或用 `TODO` 代替必要行为。
- 测试必须覆盖公共契约、关键状态、失败路径及与风险相称的产物接入验证。

尚未完成的目标不能作为已支持目标合入稳定分支。开发状态不能降低代码质量。

## 三、命名

名称必须描述当前领域职责，不能描述开发过程。

- 仓库目录和插件 ID 使用小写短横线格式。
- 各语言内部标识符遵守该语言的正式命名约定。
- 可被同一宿主加载的模块、包、产品和产物必须具有全局唯一、带插件归属的名称。
- 同一能力在契约、原生实现、适配器、测试和文档中使用同一稳定术语。
- 本仓库自研插件的反向域名标识使用 `com.sandrox.<plugin>`；共享测试应用使用 `com.sandrox.integratedplugins.<host>`。

内部文件、类型、函数、字段、模块、目录和产物禁止使用：

- `v1`、`v2`、`v3`、`phase1` 等阶段或时间顺序名称；
- `p1`、`p2`、`p3` 等优先级名称；
- `new`、`old`、`legacy`、`temp`、`final`、`backup`、`copy` 等替换历史名称；
- `misc`、`helpers2`、`utilsNew` 等含义模糊的容器名称。

真实的协议版本、Schema 版本、语义化包版本或供应商强制符号可以保留版本信息，但必须代表外部事实，不能借此表达内部迭代阶段。

`test`、`demo`、`example`、`fixture`、`mock` 只允许用于确实承担对应职责的隔离文件或目录。测试替身和测试资源不得进入运行时产物。两个原生测试工程属于真实测试工程，因此其名称可以使用 `test`。

## 四、严格边界

1. 未知字段、未知枚举、错误类型、越界数值和畸形数据必须明确失败。
2. 禁止从相似字段猜值、连续尝试多个别名、静默修正非法输入或把一种单位和格式猜成另一种。
3. 大小写、单位、标识符、字节序、时间和平台值只能按权威契约转换，并必须有测试。
4. 禁止捕获错误后返回空对象、空集合、默认成功、无关缓存或伪造能力。
5. 默认值只有在公共契约明确、确定、已记录且有测试时才允许存在。
6. 不可用信息必须按契约表示为省略、空值、不支持或明确错误，不能捏造。
7. 原生到公共契约的映射必须显式。出现未映射的新值时必须暴露明确状态，不能归入“最接近”的旧值。
8. 重试、缓存、恢复和离线行为必须是可观察、有边界的正式能力，不能成为隐藏异常的手段。

## 五、最小且干净的变更

1. 每次只完成目标所需的最小完整内容。
2. 禁止顺手重构无关代码、全局格式化、预先抽象未来需求或创建未来平台骨架。
3. 新实现被接受后，旧实现必须在同一变更中移除。禁止长期保留新旧双轨、废弃别名、双读、双写和影子实现。
4. 旧仓库行为和历史探索实现不是兼容要求。
5. 只有当前 `plugin.yaml` 明确声明、当前外部环境确实要求并且能够完整验证的适配才允许存在。
6. 修改公共依赖时必须验证所有受影响的已声明目标，但不能借机扩大未受影响目标的工作范围。

## 六、合理模块化

禁止出现职责失控的千行、万行巨型文件，但不设置机械行数上限。

出现以下情况时应按模块拆分：

- 存在多个互不相关的变化原因；
- 混合了契约、平台实现、桥接、呈现或打包职责；
- 管理了彼此无关的生命周期或状态机；
- 无法在不构造无关依赖的情况下独立测试；
- 无关修改长期集中到同一文件并产生冲突；
- 对外暴露了本应封闭的内部细节。

一个内聚行为不能只为缩短文件而拆散。禁止大量单函数包装文件、无意义转发层、被分割的状态所有权，以及为了理解一个行为必须跨越大量小文件的结构。

模块应具有单一清晰职责、明确依赖方向、最小公开表面和稳定边界测试。不能用笼统的工具类或公共杂物目录代替领域模块。

## 七、本地数据库

仓库拥有的本地开发、验证、模拟器、容器和测试数据库都视为可丢弃数据。不能为了保留这些数据或兼容旧数据库库版本而加入：

- 兼容迁移；
- 版本探测和降级读取；
- 双 Schema 或双写；
- 静默修复；
- 猜测式数据转换。

本地 Schema 或数据库依赖不兼容时，应优先提出明确重建，而不是增加兼容代码。

任何删库、清库、截断、重建、重置或破坏性迁移，在执行前都必须取得用户的明确二次确认。请求确认前必须只读解析准确目标，并说明：

1. 数据库身份和精确位置；
2. 环境及其属于本地非生产数据的证据；
3. 即将执行的准确操作；
4. 数据损失范围；
5. 恢复方式，或明确说明不可恢复。

禁止使用宽泛目录、未解析变量、通配符、用户主目录或含糊服务名作为删除目标。本规则不授权处理远端、预发布或生产数据。

消费者应用的正式运行时数据迁移属于独立产品能力。只有插件明确拥有该职责时，才能经过单独设计、声明和完整测试后实现。

## 八、清单与产物

每个插件必须有符合 `standards/plugin-manifest.schema.yaml` 的 `plugin.yaml`。

- `targets` 是正向支持清单，未出现即表示不支持。
- 未知清单字段必须被拒绝。
- 每个目标必须声明规范源码、能力、确定的构建命令、验证命令和一个或多个明确产物。
- 公共契约使用真实版本值；平台扩展不能改变公共字段语义。
- 跨平台测试向量验证行为一致性，不要求源码相同。

每个目标产物必须能够在不夹带无关目标内容的情况下独立生成和发布。一个目标确实提供多种发布格式时，可以声明多个产物。

生成内容统一进入 `dist/<target-id>/` 并由 Git 忽略。构建缓存、IDE 状态、本机 SDK 路径、测试工程和无关平台内容不得进入发布产物。

共享测试工程按交付目标消费最终产物：Android 使用 AAR，iOS 使用 XCFramework，HarmonyOS 使用 HAR，React Native 与 Web 使用 npm tarball，UniApp 使用待发布的原生插件包。测试通过后发布同一字节序列的文件，禁止重新构建一个未经测试的发布副本。

版本和包标识必须来自明确的权威来源，禁止手工维护多份并逐渐漂移。市场元数据、权限、隐私声明、最低系统版本、架构和外部依赖都属于产物契约。

## 九、验证与完成条件

验证必须沿依赖关系展开：

- 契约和值逻辑执行单元测试和测试向量校验；
- 原生生命周期或硬件能力执行平台构建、静态检查和必要真机验证；
- 桥接代码验证框架构建、数据和错误传播；
- 打包变更检查最终内容，并由干净消费工程真实接入；
- 配置注入验证最终生成工程，不能只测试转换函数。

共享测试工程必须覆盖当前插件声明目标适用的首次打开、重复打开、生命周期恢复、错误传播和产物加载。涉及媒体与手势的插件还必须覆盖本地确定性资源、远程加载中、失败与重试、缓存命中，以及尺寸和裁切差异明显的测试向量。

因硬件或授权 SDK 缺失而无法执行的必要验证，必须明确报告为“待验证”，不能声称通过。

变更完成时必须同时满足：

- 命名符合规范；
- 非法输入明确失败；
- 没有隐藏兜底和历史兼容；
- 模块既没有职责失控，也没有机械碎片化；
- 所有受影响的已声明目标完成适用验证；
- 最终产物内容准确；
- 文档、YAML、Schema 与实现一致；
- 生成文件和敏感内容未进入 Git；
- 若执行过本地数据破坏操作，已取得明确二次确认并报告结果。
